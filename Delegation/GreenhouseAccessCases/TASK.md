# Gemini: механическая проверка геометрии расширений теплицы

Читать только `Tools/Build/GreenhouseAccessSnapshot/` и SNAPSHOT.json. Писать только в `Tools/Build/GeminiGreenhouseAccessCases/`. Не менять рабочий код, XML, DLL, Git, игру, настройки/сохранения и прежние отчёты. Без сети, установки пакетов и запуска игры/DLL. Можно выполнить собственный Python3скрипт внутри выходной папки, без сторонних пакетов.

Нужно независимо проверить чистую клеточную геометрию, НЕ симулировать движок: старый прямоугольник с периметром остаётся стоять, пока новый оплачиваемый периметр/опоры/крыша не закончены. Старые стены могут отрезать новые полосы от прохода. Алгоритм должен давать каждой отдельной новой секции внешнюю дверь, через которую строители смогут закончить крышу. Только затем снимаются внутренние перегородки. При расширении на1клетку пустой новой секции может не быть: новая посевная клетка — бывшая стена. Размер4..64; запрещено пересечение с другой теплицей/зоной.

`CASES.json`:20–28сценариев с oldRect/newRect, смещением границ, количеством новых свободных связанных секций (4-соседство), проходами/дверями, новыми периметральными клетками/опорами, expectedCanPlan и конкретным объяснением. Малые4×4,6×6,8×8 и большие14×14,32×32,64×64; расширение по каждой стороне, на1/2/6клеток, одновременно противоположные стороны и угол, выход за64, пересечение иной теплицы. Не использовать логику Codex как единственный oracle: сделать отдельный BFS по свободным клеткам, исключив старые стены/периметр и будущие опоры, проверить связь каждого нового пространства с внешним миром через двери. Не объявлять CanReach движка проверенным.

`REPORT.md`: до10конкретных контрпримеров/проверенных свойств с координатами; отнести выводы только к снимку. Если примеры проходят, так и написать, не придумывать дефекты. Чётко отделить математическую доступность от рабочих задач/температуры/стоимости ресурсов в игре. Приложить `check_geometry.py` и вывод его проверок. Никаких правок кода.
