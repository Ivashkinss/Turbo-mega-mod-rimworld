# RestaurantMenuImplementation — большой следующий этап (ориентир 2–3 часа)

## Порядок и цель
Выполняй ПОСЛЕ завершения FactionRansomCorrections и SalesScanCorrections. Пользователь попросил ещё один обширный самостоятельный этап на ночное дежурство. Сделай настоящий компилируемый кандидат меню ресторана из нескольких блюд с учётом диеты и бюджета гостя. Не заканчивай общим аудитом. Если результат качественно готов раньше 2–3 часов — сдавай, не имитируй длительность и не жди искусственно. Не добавляй произвольные несвязанные функции ради объёма.

Сейчас Building_ServiceCounter.Meal выбирает единственный ThingDef, а RestaurantService.FindFood фильтрует t.def == counter.Meal. В диалоге ресепшена страница ресторана также выбирает только один вид. Новая функция должна давать колонии несколько блюд в меню и гостю возможность найти подходящую порцию, а не голодать из-за неподходящего единственного блюда.

## Изоляция
- Неизменяемый вход: `Tools/Build/RestaurantMenuImplementationSnapshot/`, база commit 3f25dcf. Сначала сверь SNAPSHOT.json. Не используй изменяющийся рабочий Source или кандидат выкупа вместо снимка.
- Писать ТОЛЬКО `Tools/Build/GeminiRestaurantMenuImplementation/` и свой `Tools/Build/GeminiWorkerState/RestaurantMenuImplementation.json`. Рабочие Source/Defs/Languages/Assemblies, Git/QUEUE, игру, пользовательские настройки/сейвы не менять. Не запускать игру, GUI, фоновые службы; сеть/установка инструментов не нужны.
- Compiler и существующие библиотечные/игровые reference DLL читать можно. Для метаданных пользоваться Mono.Cecil read-only; НЕ исполнять Assembly-CSharp.dll в PowerShell/standalone процессе.
- Не накладывать незавершённые соседние кандидаты. При последующей интеграции Codex сам объединит минимальные пересечения.

## Игровой результат
1. Всё управление меню только через ресепшен → «Настройки служб комплекса» → ресторан. Никаких новых зданий, нижних вкладок и областей. Для отдельно стоящей стойки вне комплекса сохранить существующий одиночный режим как совместимый fallback, не переписывать его UI без необходимости.
2. В комплексе можно включить несколько видов готовых блюд из текущих DefDatabase по существующему RestaurantMeals.Prepared. Варианты модов/DLC находить динамически, без фиксированного списка Simple/Fine/Lavish и названий рас/фракций. Исключённые существующим Prepared наркотики/сырые продукты не добавлять.
3. Предлагается компактный scrollable диалог с поиском по локализованному названию, галочками выбора, понятными «Выбрать всё» / «Очистить». Видна пустота меню и отсутствие подходящих готовых порций. Выбор блюда не создаёт ни еду, ни заказ на приготовление. Повар по-прежнему готовит через стандартные задания кухни; официант не готовит. Без выдуманных звёзд, кулинарных дипломов и новых валют.
4. Старые сохранения мигрируют ровно один раз из restaurantMeal (или Simple, если старого значения нет). Явно очищенное меню остаётся пустым после save/load — нельзя каждый тик возвращать Simple. Новая стойка начинает с совместимого базового меню. Удалённые/незагруженные ThingDef и дубликаты безопасно очищаются; не подменяй пропавший выбранный модовый Def случайной едой. Старый save key сохраняется ради совместимости.
5. Новый заказ рассматривает только реально доступные порции включённых блюд. Обязательны существующие проверки RestaurantMeals.Stock, Edible, FoodPolicy и FoodUtility.WillEat, ингредиентов конкретной порции, свежести/запрета, резерваций, места и кошелька гостя. Неподходящая дорогая порция не должна закрывать доступ к дешёвой подходящей.
6. Выбор детерминированный, без новых вызовов RNG: среди подходящих и доступных по цене порций предпочти более высокую нативную FoodPreferability; затем существующее предпочтение склада комплекса перед холодильником колонии, затем расстояние до стойки, затем thingIDNumber для стабильного равенства. Это стартовая понятная эвристика, не обещать полноценную нативную FoodOptimality всех модов. При единственном пункте меню поведение должно совпадать с прежним, кроме явного стабильного tie-break.
7. Все действующие пространственные правила сохраняются: служебная зона гостям закрыта; официант может принести из разрешённых холодильников колонии, в том числе в режиме «Только комплекс» как существующее исключение снабжения; приватный стол номера обслуживает своего постояльца, палатные столы не обслуживаются.
8. Заказ фиксирует ThingDef выбранного блюда и цену при принятии. Смена меню, тарифа или количества доступных блюд влияет только на НОВЫЕ заказы. Нельзя при замене пропавшей порции принести другой вид блюда по старой цене. Допустима другая подходящая порция того же зафиксированного Def по существующим правилам, либо безопасная отмена. Обрати внимание: старый ForWaiter вызывает FindFood(counter,guest,waiter,order) с counter.Meal — это место нужно исправить для фиксации заказа.
9. Перед реальной доставкой повторно проверяются текущая диета/ингредиенты, существование и резервирование порции, деньги, гость и официант. Если за это время диета изменилась и порция запрещена — заказ отменяется/безопасно перестаёт обслуживаться, запрещённую еду не вручать. На неё не переключаться тайно с изменением цены.
10. Деньги/эскроу/доход/самовыкуп НЕ перерабатывать: прежняя физическая оплата при доставке, сохранение выручки при блокировке сброса, отсутствие двойных начислений, 50% существующего consumable credit. Hospitality free-food и ресторанный тариф 0% сохраняются, бесплатная еда не создаёт серебро или зачёт. Никаких комиссий повару из воздуха. Продажи/оптовики/гостиничный тариф не менять.
11. Не портить уже сохранённые активные заказы. Existing order.mealDef и price — приоритет над изменённым меню. Сохранение/загрузка списка меню и заказов не добавляет повторных заказов/квитанций, job.count остаётся идентификатором заказа, а количество переносимой еды явно 1.
12. RU/EN строки полные и параллельные; параметры одинаковые. При длинных списках/названиях диалог не выходит за экран, нативные GUI.Font/Anchor/Color/WordWrap восстанавливаются после рисования. Подсказка объясняет выбор, пустое меню, питание по диете и неизменность принятых заказов. Не скрывать диетические ограничения или личные деньги гостя.

## Приёмочные случаи (подготовить для реального кода)
- Старое сохранение с одним выбранным блюдом мигрирует один раз; повторная загрузка не расширяет меню.
- Явно пустое меню не возрождает Simple.
- Два блюдa, одно запрещено FoodPolicy: выбирается разрешённое.
- Один и тот же Def с разными ингредиентами: запрещённая гостю порция не выбирается.
- Более качественное/предпочтительное блюдо не по карману, дешёвое доступно: оформляется дешёвое.
- Все блюда недоступны по цене/диете/свежести: нет фиктивного заказа/списания.
- Одинаковая пригодность — стабильный выбор без RNG; вариант на складе комплекса прежде колониального fallback.
- Два гостя и одна порция: нет двух действующих заказов на неё.
- Меню и тариф изменены после принятия: блюдо и price принятого заказа прежние.
- Исходная порция исчезла: замена только того же Def, иначе безопасная отмена.
- Диета изменилась перед передачей: запрещённая порция не вручается и серебро не списывается.
- Прерывание/мобилизация/уход гостя/разрушение стойки не теряют еду/серебро.
- Бесплатное питание/0%: нет нового серебра или self-buyout credit.
- Blocked receipts и save/reload активного заказа/меню сохраняют escrow и уникальность начисления.
- Служебный склад, приватный стол, клиника, режим персонала: прежние ограничения.
- Модовое блюдо/исчезнувший Def/длинное название: безопасная миграция и читаемый UI.

До сдачи: проверь, что Candidate содержит обещанный КОД, а сборщик использует его. Не подтверждай работу отдельным зеркальным Mock алгоритмом. Если возникают реальные блокеры API — запиши точную ошибку, попробуй минимальный ремонт, не маскируй её заглушкой или unconditional true. Обнови свой WorkerState после готовности; QUEUE не менять.
