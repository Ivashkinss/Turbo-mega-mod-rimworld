# FactionRansomPolicyImplementation — индивидуальная вероятность выкупа фракциями

Пользователь ранее явно попросил: сейчас шанс50%, позднее индивидуальные настройки для каждой фракции, с поддержкой добавляемых фракций. Сделай настоящий компилируемый самостоятельный кандидат следующего этапа (не только аудит). Карательные рейды, бунты и сюжетные происшествия отложены; не добавлять их.

## Уточнение границ после ACK
В WorkerState упомянуты «автоматический/ручной режим, ценовые пороги». ЭТО НЕ ЗАКАЗАНО. Нужны только вероятность согласия0..100% и исключения по конкретным фракциям. Не добавляй автоматическое принятие/выплату/переговоры, ценовые пороги, изменение цены или иной policy engine. Сумма и OfferRansom остаются прежними. Если уже начал лишние функции — убери их до сдачи.

## Изоляция
Читать НЕИЗМЕНЯЕМЫЙ Tools/Build/FactionRansomPolicySnapshot/ и сверить SNAPSHOT.json. Запись ТОЛЬКО Tools/Build/GeminiFactionRansomPolicyImplementation/ и Tools/Build/GeminiWorkerState/FactionRansomPolicyImplementation.json. Source/Defs/Languages/Assemblies корня, Git/QUEUE, игру, настройки/сейвы не менять. Сеть/GUI/игру не запускать; compiler/ref DLL можно читать. Assembly-CSharp только Cecil metadata, не исполнять в shell.

## Результат игрока
1. Сохранённая в текущем мире настройка вероятности согласия на выкуп: общий исходный шанс50% + необязательные исключения0..100% для конкретных фракций. Сброс исключения возвращает общий шанс. UI только через ресепшен → существующее управление обычным самовыкупом/фракционным выкупом (одна кнопка настроек внутри этого меню, не новое нижнее меню). Не изменять окно Readiness или остальные вкладки/экономику.
2. Фракции перечислять динамически из мира, без имён Fallout, Def-списка или новых внешних зависимостей. Разные экземпляры одной FactionDef должны иметь независимые исключения; само FactionDef не использовать как единственный ключ. Фракцию игрока исключить; показать недоступные/уничтоженные безопасно или скрыть, не уничтожая существующие транзакции. Будущие модовые фракции автоматически подхватываются.
3. Использовать существующий FactionRansoms GameComponent для сериализации настроек (defaultChance int + List с Faction reference и overrideChance). Никаких настроек в сейвах других миров. Сохранение/загрузка, отсутствующие теги старого сейва, null/lost refs, некорректные0..100 и дубликаты правил обрабатываются детерминированно и безопасно. Новый компонент не нужен.
4. Существующее WillFactionAccept использует PushState(seed) + Rand.Chance(0.5f) + PopState. Сохрани seed и восстановление RNG; заменить только вероятность разрешённого нового предложения. Не использовать глобальный Rand без Push/Pop. При исходных50% новые ответы должны точно совпасть с прежним алгоритмом. 0% всегда отказ,100% всегда согласие.
5. КРИТИЧНО: настройки влияют ТОЛЬКО на новые предложения; уже сохранённые offered/agreed/state/escrow/placedAmount, договор, исходная фракция, выручка, история обмана и освобождение НЕ пересчитываются. Нельзя разрешить повторное предложение или переигрывание отказа изменением настроек. OfferRansom фиксирует ответ один раз. Не менять оплату, возврат, освобождение и денежные guards ради настройки.
6. UI с прокруткой/поиском при длинном списке, общее значение и индивидуальные исключения, понятный сброс, явная подпись «только новые предложения». Шаг5% + границы0/100 достаточно; числовой ввод не обязателен. Методы изменения валидируют0..100. GUI state и scroll group restore try/finally. Длинные имена фракций не перекрывают элементы.
7. Все тексты paired RU/EN с равными placeholders. Общие legacy тексты не должны ложно утверждать50% для каждого предложения при override; текущий шанс показывать в соответствующем предложении/UI через реальные данные. Не перезаписывать посторонние языковые файлы и не дублировать ключи. Насилие/сексуальные услуги сюда не добавлять.
