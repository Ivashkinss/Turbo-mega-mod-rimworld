# Gemini: бинарные точки расширения для будущих VIP

Предыдущая задача VipGuestReadinessSurvey сопоставила исходники. Теперь нужна отдельная механическая сверка этих точек с реальными включёнными DLL1.7 и1.6: это подготовка следующего этапа VIP, не его реализация. Текущая ревизия досье/меню/теплиц уже прошла807проверок в24целевых игровых шагах, Codex завершает публикацию.

Читать Tools/Build/VipGuestBinaryHookSnapshot/ (источники/хэши), обе Components/Hospitality/{1.7,1.6}/Assemblies/Hospitality.dll и доверенную Components/Harmony/1.6/Assemblies/0Harmony.dll только как поставщик Cecil. Метаданные DLL смотреть через Mono.Cecil, не исполнять код Hospitality/Assembly-CSharp через Assembly.Load/Reflection. Библиотеку Harmony как существующий доверенный инструмент инспекции использовать можно; проверить её SHA256 по SNAPSHOT.json. Игра/сеть не запускаются.

Писать только Tools/Build/GeminiVipGuestBinaryHookAudit/ и status Tools/Build/GeminiWorkerState/VipGuestBinaryHookAudit.json по GEMINI-WORKER.md. Source/XML/DLL/Git/настройки/сохранения и предыдущие отчёты не менять. Никаких изменений баланса или бизнес-решений за пользователя.

Создать API.json (не более12 узлов), ORDER.md (до60строк), REPORT.md. API для2версий: тип, точное имя метода/поля, доступ, static/instance, возвращаемый тип, все имена/типы параметров, generic/overload, наличие в DLL, различия со снимком исходников. Основные узлы: IncidentWorker_VisitorGroup.GiveItems / GenerateNewPawns / CreateLord / CreateLordCore; CompGuest.Arrive и lastBedCheckTick; JobGiver_ClaimBed.TryGiveJob; JobDriver_ClaimBed.MakeNewToils и место завершения оплаты; Building_GuestBed.GetRentalFee. Не больше12 записей по узлам, можно вложить2версии в одну.

По IL доказать относительный порядок: генерируются/передаются серебро и товары, создаётся Lord, вызывается Arrive, задаётся lastBedCheckTick, выбирается кровать, списывается цена. Сопоставить с нашими GuestDossierHooks/HotelBillingHooks: какой момент уже содержит принятый после blacklist список; какие callbacks бывают при восстановлении группы и при госпитализации. Нельзя предлагать повторно выдавать деньги/перебрасывать VIP при каждом Arrive/load. Помнить, что blacklisted пешка может уже быть заспавнена и затем уйти пешком; исключения включают текущий визит и recoveredOnMap, не только пациентов.

Точно выписать IL-формулу задержки кровати:4тика на монету и последующий lastBedCheckTick=now+500, если подтверждается. Не называть секунды при произвольной скорости игры. Уточнить поля, позволяющие потом ограничить VIP-задержку без изменения обычных гостей, но код патча не писать и значения кэпа не назначать. Проверить ветки spaceFor>0/==0: при положительной вместимости сумма обрезается, излишек не выбрасывается; отдельный fallback на пол только при нулевой вместимости.

В отчёте разделить факты/IL-доказательства, возможные точки патча и нерешённые решения. Не объявлять VIP внедрёнными, не планировать сюжетные происшествия, не смешивать CompanyService с корпорацией. Не выводить полные дампы DLL; сохранить только нужные короткие IL-отрывки/смещения. Временные вспомогательные скрипты можно оставить в своей выходной папке для воспроизводимости.
