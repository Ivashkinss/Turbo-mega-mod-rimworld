Пользователь поменял приоритет: сначала стратегические форпосты, региональные фракции и мировые караваны. MinutemenHuntersPrototype уже сдан, его не менять и не интегрировать. Ориентир1–2часа содержательной работы. Нужен законченный КАНДИДАТ ЯДРА, не один план/аудит. Прочитать Documentation/STRATEGIC-SETTLEMENTS-DESIGN.md целиком: отличать требования пользователя от предложений Codex.

## A. Выбрать основу по реальному коду, не названиям
Первичные URL в design. Начать с существующей Components/VanillaExpandedFramework/{1.6,1.7}/Assemblies/Outposts.dll и VOE. Проверить лицензии/README/атрибуцию; зафиксировать URL, полный commit SHA, версии About/assembly refs, фактические API в SOURCES.json. Для Empire/RimWar/FactionControl достаточно ограниченной проверки подходящих подсистем/конфликтов, не инвентаризации тысяч файлов. Решить, какие механики переиспользуем/оборачиваем и что дописываем. Не копировать текстуры/код без ясного основания на повторное использование. Если условия мешают копированию, описать независимый адаптер к уже включённой библиотеке/собственную реализацию и конкретный объём.

Не устанавливать целиком4мировых оверхола. RimWar может менять генерацию обычных рейдов/караванов и threading; это отдельная интеграция, не молчаливая новая зависимость. Кластеризацию и видимость мировых групп на этом этапе описать в INTEGRATION-PLAN.md с owning entry points и риском старых сейвов, не переписывать текущий мир.

## B. Реализовать компилируемое ядро кандидата
1. Один собственный WorldObject/обёртка проверенного Outposts API, четыре специализации. Создание настоящим караваном на допустимой клетке, минимум2подходящих реальных пешки. Передача людей атомарная, с сохранением идентичности/экипировки/инвентаря/родственных связей; никаких копий Pawn и одного человека сразу в двух контейнерах. Возможность забрать работников обратно настоящим караваном; не потерять последнего работника/WorldObject без явной обработки его груза.
2. Уровни1..10, player capacity=level+1. Повышение оплачивается настоящим серебром из доступного взаимодействующему форпосту контейнера/каравана, не из абстрактного счётчика и не чужой карты. Для ПРОТОТИПА предложить настраиваемые через Def параметры500×1.6^(nextLevel-2), округление вверх; явно отметить, что пользователь ещё не утвердил эти цены. Проверка10уровня, нехватки денег/места, сохранения и защита от повторного списания.
3. Суточный трудовой бюджет60000ticks. Руды=Mining, дерево/плантация=Plants, фабрика=Crafting; специализация поста наблюдения отдельная. Нормы и разрешённые продукты data-driven. Пример-эталон: Mining150 даёт100plasteel/day для одного направления. При равном делении сопоставимых направлений сохранять пример100steel ->50steel+50wood, но не приписывать нулевому навыку ненулевой труд. Делить общий бюджет ДО расчёта выпуска, один человек не работает на100% одновременно в каждой выбранной строке. Дробные остатки сохраняются, снятие/смена назначения не чеканит выпуск заново.
4. На выходе настоящие Thing в owner/container, корректные stack limits, масса/резервации, охрана владения. Посуточная отправка в выбранную домашнюю колонию: допустим native транспортный pod для первого кандидата, но явно назвать это упрощением; невидимый «караван» не выдавать за будущую мировую группу RimWar. При отсутствии карты получателя/места товар удерживается, не исчезает и не дублируется. Реальные движущиеся караваны — отдельный последующий модуль.
5. Для фабрики — реальные существующие рецепты/исследования/ингредиенты; доставка сырья в форпост, атомарное списание за фактическую продукцию. Если ингредиентов нет — соответствующая доля простаивает без бесплатных компонентов. Hyperweave не имеет обычного vanilla recipe: не выдумывать существующий рецепт; отдельный предлагаемый Def обозначить как неутверждённый/выключенный по умолчанию либо честно отложить эту позицию.
6. Сохранение уровня/пешек/контейнеров/выбора/суточного срока/остатков/отправки. Не считать сутки повторно после save/load; time jump обрабатывать ограниченно, без бесконечных циклов и миллионных стаков. При загруженной карте форпоста не начислять абстрактную продукцию параллельно работе тех же людей. Старые сейвы не двигать/пересоздавать; начальное ядро не создаёт ни одной новой точки без команды игрока.
7. Небольшой понятный интерфейс WorldObject: состав/лимит, уровень/цена улучшения, специализация, выбранные продукты/ожидаемо за сутки, запас сырья/готового, получатель. RU/EN. Не плодить отдельные нижние вкладки для каждого форпоста. Обычные колонисты в других системах/караванах и гостиничные роли не меняются.

## C. Что обязательно спроектировать для следующих этапов
Общий level/tier интерфейс для NPC поселений, отдельно технология/стиль. Реальная посещаемая сохраняемая база растёт при уровнях: площадь/кровати/мебель/защита. Нельзя объявить это сделанным, имея только integer Level в инспекторе. Для первого ядра допустим рабочий маленький посещаемый форпост через native map generator или чётко ограниченная world-only версия, но тогда полный пользовательский результат НЕ готов: перечислить необходимые следующие изменения и точные owning API. Не регенерировать загруженную карту поверх имущества. Стратегия кластеров новых миров/новых точек; безопасное отдельное обсуждение миграции старых. Движущиеся группы имеют владельца/маршрут/цель и не дублируют vanilla storyteller рейды. Сторожевой пост предлагается для разведки/предупреждения; не вводить обязательный fog of war вместо запрошенной видимости всего мира.
