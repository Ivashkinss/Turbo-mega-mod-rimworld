Модель одной сделки с фиксированным количеством (уменьшение количества выбирает будущий вызывающий код):
1. Вход: id сделки, флаги duplicate/complexActive/factionFriendly/arrived/publicHandover/staffDeliveryReady, storagePublic, requestedCount, stockCount, reservedCount, unitMarketValue, itemUnitMass, silverUnitMass (обычно "0.008"), carriers[{id,eligible,capacity,currentMass,silver}], transferSucceeded, dropParts[] (целые числа монет, успешно сброшенных после передачи). currentMass уже включает экипировку, другие вещи и всё серебро носильщика. Не складывать массу серебра второй раз. Carrier здесь означает произвольного носителя, а не enum TraderCaravanRole.Carrier.
2. Все количества — целые (не bool), requestedCount>0; stock/reserved/silver/dropParts>=0. Идентификаторы носителей уникальны. capacity/currentMass/itemUnitMass>=0, silverUnitMass>0, unitMarketValue>0; все значения конечные. currentMass >= silver*silverUnitMass. NaN/Infinity/отрицательное значение или цена >2147483647 => отказ до изменения денег/товара. eligible задаётся адаптером реальных Pawn/CanEverCarryAnything/доступности; не вводить проверку packAnimal или списка фракций в модель.
3. Если duplicate=true: результат duplicate, 0 новых передач, 0 новой выручки; исходное состояние носильщиков сохраняется. Не имитировать повторное списание. Если прочие входы невалидны, приоритет результата invalid, затем duplicate, затем проверки ниже.
4. Нужны активный комплекс, дружественная/нейтральная фракция, физическое прибытие к доступному публичному месту. Для закрытого склада дополнительно нужен staffDeliveryReady. Иначе refused без изменений. requestedCount <= max(0,stockCount-reservedCount); резервирование снижает запас, но не создаёт денег.
5. Quote=ceil(requestedCount*unitMarketValue*Decimal("0.55")) за ВСЮ партию; не округлять каждый предмет отдельно. Сумма реального silver только eligible носителей должна покрывать Quote. Не использовать исходный запланированный бюджет, если деньги уже потрачены/утрачены.
6. План оплаты: сортировать eligible по id (обычные ASCII строки, сравнение лексикографическое), последовательно забирать min(остаток Quote, carrier.silver). При таком списании у конкретного носителя освобождается debit*silverUnitMass массы. Деньги пока лишь запланированы — до успешной передачи не считать доходом.
7. План размещения: в том же порядке id использовать max(0,capacity-(currentMass-debit*silverUnitMass)). Для itemUnitMass>0 помещается floor(свободная масса/itemUnitMass) целых единиц; для нулевой массы — весь оставшийся заказ. Партия из нескольких единиц делится по носителям; ОДНА тяжёлая вещь не делится на куски. Если все requestedCount не помещаются, отказ без списания и передачи, даже когда общая сумма свободного веса больше массы вещи. Это определённая детерминированная модель, не поиск оптимального распределения платежа по всем возможным вариантам.
8. Если transferSucceeded=false: состояние cancelled, все исходные деньги/товары сохранены, эскроу/выручка/новый доход=0 (абстрактный успешно выполненный откат; реальный TryTransfer/rollback проверит Codex в игре).
9. При успехе: состояние completed, товар передан в инвентари по плану, из stock вычтено requestedCount, серебро списано по плану. Эскроу сначала Quote, доход ещё 0. Последовательно обработать dropParts: каждая часть должна быть <= текущего остатка эскроу, иначе invalid ВЕСЬ сценарий до изменений. Новая физическая выручка и новый доход равны сумме dropParts; остаток эскроу=Quote-сумма. Не вычитать доход второй раз из денег колонии и не создавать комиссию/самовыкуп.
10. Выходы: status, quote (0 при invalid/duplicate; иначе вычисленная цена), debitByCarrier, goodsByCarrier, finalSilverByCarrier, finalMassByCarrier, finalStockCount, deliveredCount, escrow, physicalReceipts, colonyIncome. При отказе/отмене планы debit/goods в выходе нулевые, состояние исходное. При успехе finalMass=currentMass-debit*silverUnitMass+goods*itemUnitMass. У неeligible носителей изменений нет. Доход учитывается только после успешной выдачи и физического сброса серебра.
