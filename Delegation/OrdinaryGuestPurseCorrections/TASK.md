## Замечания Codex

1. **OP-01: переполнение до clamp.** CalculateTarget приводит Math.Round(scaled) к long ДО ограничения10000. Для float.MaxValue результат выходит за long и не даёт разумные10000. Сначала проверить/ограничить double, потом преобразовать. Конечный положительный огромный множитель ->10000, NaN/Infinity/negative ->0. Не отбрасывать произвольно маленькие положительные множители через0.0001: округлять математически, настоящий0 ->0. Добавить прямые проверки production-метода для0/0.5/1/2/float.MaxValue/NaN/Infinity/negative.
2. **OP-02: отсутствует native inventory-space guard.** Масса недостаточна: provider ItemUtility.GetInventorySpaceFor учитывает CompInventory через InventoryCapacityCompatibility. Уважать этот owning API через безопасную reflection/кеширование без compile-reference Hospitality; принимать минимум дефицита, массы и native space; размер probing stack должен быть настоящим желаемым extra. Никаких самостоятельных fake-API/падения на отсутствие обычного optional CompInventory. VIP-код вне scope.
3. **OP-03: тест не соответствует реальному GiveItems.** Native GiveItems добавляет собственные food/backpack/silver/junk КАЖДЫЙ вызов. Нельзя считать tripAdded==target-20 без учёта native silver, нельзя ожидать500 после native генератора, либо0 при multiplier0: native минимум10 намеренно остаётся. Изолировать и измерять именно НАШУ добавку после native генерации (реальный Harmony observation до ItemsGiven либо иной доказуемый метод); нельзя отключать native generator, подменять результат или вызывать fallback вместо отсутствующего GiveItems. При multiplier0 наш tripTarget/tripAdded==0, native серебро допустимо. Повтор нативного генератора не обязан оставлять общий баланс неизменным, но наш guard/target/added не меняется и наш top-up не повторяется. Отдельно прямой повтор PrepareTrip/Prepare обязан не создавать монет. Учитывать рандомные вещи при проверке вместимости. Полная генерация может довести VIP до capacity, не гарантировать минимум1500 без контролируемой реальной вместимости.
4. **OP-04: fake lifecycle.** Вектор8 вызывает Settle напрямую и остаётся на той же карте — это не естественная новая поездка. Сделать реальный native CreateLord/Arrive, Leave/выход либо owning End через наблюдаемый реальный despawn + Synchronize, затем новый spawn/GiveItems/CreateLord. Не вызывать ResetTrip/Settle напрямую ради результата. Save/load: сохранить реально зарегистрированного гостя, а не пешку без Lord/Current; иначе Synchronize может корректно сбросить прерванный подход. Проверить при reload неизменные поля/кошелёк, затем реальный конец/новую поездку. Добавить блокировки Current, blocked, clinic, wholesale как достижимые fixtures или честно перечислить непроверенные. Удалить прямой fallback из CallGiveItems, отсутствие метода должно проваливать fixture.
