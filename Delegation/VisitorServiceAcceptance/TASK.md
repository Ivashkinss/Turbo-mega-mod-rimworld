# VisitorServiceAcceptance — сквозной визит и расход реального бюджета

Следующая задача после OrdinaryGuestPurseCorrections. Запись только Tools/Build/GeminiVisitorServiceAcceptance/ и Tools/Build/GeminiWorkerState/VisitorServiceAcceptance.json. Вход immutable Tools/Build/VisitorServiceAcceptanceSnapshot/ (проверить SNAPSHOT.json), owning Components/Hospitality/Source и установленные reference/providerDLL читать можно. Корень/игру/настройки/сейвы/Git/QUEUE не менять, сеть/GUI/игру не запускать. Assembly-CSharp только metadata/Cecil; compiler можно. running -> done.

Нужен компилируемый КАНДИДАТ ОДНОГО native integration probe для Codex, без правок production: обычный гость с150–300 на поездку действительно пользуется несколькими службами и платит из одного кошелька, а не только проходит отдельно каждый helper. Codex сам запускает игру/добавляет runner после review. Это содержательная задача, не очередная механическая инвентаризация.

## Обязательный сценарий
1. На отдельной тестовой карте подготовить небольшой реальный готовый комплекс: спальня с гостевой кроватью30/сутки, стол/стул, ресторан с готовой едой/назначенным официантом, стойка и безопасный подход. Использовать предоставленные probes как образцы fixture, не копировать огромную несвязанную систему. Избегать уничтожения VoidMonolith и ссылок на despawned unsaved пешек.
2. Посетителя получить через настоящий native VisitorGroup incident либо доказанную нативную цепочку SpawnPawns/GiveItems/CreateLord/arrival, оставить обычным (VIP0), multiplier1, зафиксировать настоящее количество серебра в inventory. Никакого добавления ему серебра после генератора для прохождения сценария.
3. Дать реальному MainThinkNodeRoot/JobTracker заселить гостя и снять первые30 серебра. Затем добиться реального заказа/доставки ресторанного блюда официантом через owning JobDrivers. Проверить вычет цены блюда, появление физического серебра/учёт, отсутствие двойного дохода, сохранение оплаченного номера. Нельзя вызывать завершение/Record/Deliver напрямую вместо игровых действий. Допустимы только настройка потребности Hunger и назначений работников, ускорение игрового времени, контролируемая тестовая погода; каждую манипуляцию назвать.
4. Save через GameDataSaveLoader в активном наблюдаемом состоянии (предпочтительно между платой за кровать и заказом/доставкой). Отдельный reload flag восстанавливает и продолжает. Guard кошелька, таймер кровати, цена уже принятого заказа, реальное серебро и доход должны сохраниться без повторной выдачи.
5. Наблюдать уход через нативный Lord/ExitMap. Не утверждать прохождение естественных суток, если deadline ускорен. Никаких прямых Settle/ResetTrip. Если природный выход/AI требует условий, явно зафиксировать ограничения, а не телепортировать гостя ради PASS.
